# Operations Readiness

Read when: closing Gate 3, writing `runbook.md`, or judging whether an admin and its backend can be run in production by someone who did not build them. It turns the runbook from a document that exists into a set of capabilities that were exercised. Gates: `OPS-1` to `OPS-20` in `quality-gates.md` (section I), and `ENG-14` for the build.

## 1. The verdict

A project is **Ready**, **Ready with named conditions** or **Not ready**. It is Ready only when no part of the runbook that decides recovery is left undecided: hosting and domains (§1), backup and restore (§5), monitoring and known limits (§9). A cell that still says "undecided", "TBD" or an unfilled `<placeholder>` at the final stage is a condition, not a pass. Each condition has an owner and a date, and the owner of the product signs a one-line risk acceptance in `qa-report.md`. The validator warns on those markers at the final stage (`--strict` makes them errors).

## 2. Backup and restore

- State **RPO** and **RTO** in numbers (for example "lose at most 24 h; back within 4 h") and say who decided them.
- A backup that was never restored is a hope. Evidence: a **dated, timed restore** into a scratch database, then a row-count and checksum comparison on the tables that matter, recorded in the runbook (date, duration, result, who). Repeat on a schedule.
- Back up everything that is not in code: the database, uploaded files and stored assets (images in the database are covered by the database backup, say so), secrets are recovered from the secret store, not from the backup.
- Backups of personal data obey the erasure window (see `privacy-and-data-rights.md`): keep them no longer than that window, or replay the deletion log after a restore. Encrypt them; name who may restore.
- The application's runtime database role must not be able to drop or alter the audit table (see `identity-and-sessions.md`, separate migrator and runtime roles).

## 3. Migrations

> **Test traps once a ledger exists:** an "idempotency" test that runs the migrations twice passes vacuously, because the second run skips every recorded file. Give the runner a replay-all mode and call it in those tests. Also test the two things a ledger exists for: two processes starting together run each file exactly once, and a failing migration stops the process before it listens.

- **Expand, then contract.** First deploy a change that the old and the new code both work with (add a nullable column, write both, backfill); remove the old shape only in a later release. "Reversible" means the expand step is harmless to roll back, not that every migration has a down script.
- A **ledger table** records each applied migration with a checksum; a changed or missing file is an error. Never re-run every file at every boot.
- One migrator at a time (advisory lock). Run migrations as a **separate command** in the deploy, not as a side effect of starting the web process.
- **A session lock does not survive a transaction-mode pooler.** A session-level advisory lock (`pg_try_advisory_lock` … `pg_advisory_unlock`) taken through a pooler in transaction mode lives on whichever server connection ran that statement; the unlock can land on another one, the lock stays until that connection closes, and the next migration or job run skips itself as "already running". Run the migrator, and any job that holds a lock for a whole run, on the **direct** database host, or use transaction-level locks (`pg_advisory_xact_lock` inside the transaction) or a lease row with an expiry. (Found by reading the proving project's code while its connection string pointed at a pooled host; not observed as a failure, and not yet changed there.)
- **A revert keeps its migration files.** With a ledger that refuses to boot when an applied file is missing, reverting a change that added a migration makes the new process exit before it listens: the host keeps the old one, so nothing breaks, but nothing rolls back either. Keep the `.sql` file in the revert commit (additive migrations make that safe: the old code ignores the extra table or column), and use the host's "redeploy an old build" only when no migration ran since that build. Say both in the runbook's rollback section.
- If a migration fails the process must **not serve** (readiness fails, the old instances keep serving); swallowing the error and continuing is a defect.
- **A database that has the tables but no ledger needs a baseline.** After comparing the real schema with what the files would build, record the existing files as applied (with their checksums) instead of running them against live data: "create if not exists" files stop being safe to run twice once an `ALTER` or a data fix is in the history. Offer the baseline as an explicit command, never as a silent boot step.
- **Set `lock_timeout` for DDL** (about 3-5 s) and retry a few times. A migration that waits for a lock on a busy table makes every later query queue behind it, and that looks like an outage. Prefer expand/contract steps that need no long lock.
- **Retry the database at boot** with a backoff for a minute or two before giving up. A hosted database that sleeps or restarts is slow to answer, and a process that exits on the first refused connection turns a short delay into a crash loop. Readiness stays red while it retries (`OPS-12`).
- Test: two instances starting at once; a failed migration leaves readiness red. The runbook rollback section must agree with this rule (a runbook that forbids rollback and a gate that demands reversibility contradict each other: pick expand/contract and say so).

## 4. Health and the System panel

- `/healthz` answers "is the process alive" and touches nothing. `/readyz` answers "can it serve": database reachable (with a short timeout), migration level current, critical dependencies. A route that returns a static "ok" is not a health check.
- Configure the platform's health probe to `/readyz` (and the restart probe to `/healthz`), **except** on a database that sleeps or bills by activity: there a probe that queries on every call keeps it awake, so point frequent probes and outside pingers at `/healthz` and let readiness answer from its last result while nobody uses the product (§13).
- **A public diagnostic route is cheap.** A route anyone may call (version, commit, uptime, memory) touches no database and makes **no outbound call**. A probe of an upstream service (does the provider answer this server's address?) belongs to the admin, behind a permission, rate-limited and audited: a public route that called the upstream on every request let anyone spend the server's standing with that upstream.
- **A system event trail.** Boot, graceful shutdown (signal, uptime, requests in flight), version change (from and to), migration applied (the names, once) and each retention run go to a small table of their own, fire and forget, with no personal data, kept about a year, and shown as a "System" view next to the audit log. It answers "did it restart, and into what?" after the host's own logs are gone. The System page's retention table is generated from the constants the purge job uses, so the page cannot disagree with the job.
- **Stopping is part of health** (`OPS-19`). On SIGTERM: readiness answers 503 `shutting_down` at once (liveness stays 200), the listener takes no new connection and answers carry `Connection: close`, running requests get a grace period, then background writers flush (metrics, the request log, credentials cached in memory) **before** the pools close, timers stop, and the process exits 0. Put a hard exit a little before the platform's kill timer (the proving project: 25 s of grace, a hard exit at 28 s, the host kills at 30 s); a second signal must not start a second shutdown, and a step that throws must not stop the next ones.
- The admin gets a **System** page even when there are no background jobs: version and build, migration level, uptime, dependency checks, last backup age, per-process limits (so the multi-instance caveat is visible), and the state of every runtime control. Excluding the jobs module must not drop this panel.
- **Show the versions side by side: the admin's own, the public app's and the API's.** "Is this user on the current version?" is the first support question, and the API build id alone (a commit hash) cannot be compared with what a user reads on their account screen. Give every deployable a plain version number that goes up with each release (a `version:bump` script, one number per deployable, shown with the build day and no time of day). The public app publishes `/version.json` (version, build id, day) with `Access-Control-Allow-Origin` and `Cache-Control: no-cache`, outside its service-worker precache, and the admin reads it (add that origin to the admin's `connect-src`, and say so in the security-headers note). If the file is missing, say "could not read it" instead of guessing. Note what the number means: it is what a **fresh load** gets; an installed app on an old version is exactly what the operator is comparing against.

## 5. Observability

- One **request id** on every route, public and admin: created at the edge, echoed in the response, written to every log line, to the error envelope and to the audit row.
- Logs are structured (JSON) on stdout; a log aggregator keeps them for the stated period. Name the **error tracker** (or say there is none and who reads logs).
- List 3-5 **symptom alerts**, each with a threshold and a recipient: error rate, p95 latency of the slowest key endpoint, failed-sign-in spike, queue age (if any), backup age. Alert on symptoms users feel, not on every cause.
- **Telemetry must explain, not only measure.** A page that says "p95 is 38 s" and nothing else sends the operator to read code. For every job that has a cheap path and an expensive fallback (a plain request, then a headless browser; a cache, then a recomputation), record on each event **which path answered and why the expensive one was needed** (a fixed reason code, never user text), and show: each kind split by path with count, failures, p50 and p95; the reasons, most frequent first; the latency distribution in a few fixed buckets; and the handful of slowest events. A health warning must **name where the figure comes from** ("slowest in Search: p95 40 s, while Details is 1 s; 34 runs needed the browser") and not just repeat it. A p95 over a few dozen runs can be a single outlier: show the count next to it.
- **List the inputs that skip the cheap path.** Every fast path has inputs it cannot serve (an optional field that is missing, a count above a limit, a new account with no data yet), and those inputs often arrive exactly when a user is new and impatient. Make the fallback reason observable, then test those inputs on purpose. Also check that the client timeout is longer than the server's worst case, or that identical requests in flight are coalesced; otherwise every client retry starts the expensive path again (not measured on the proving project: found by reading the code).
- **Keep the requests worth reading again, with a light trace** (`OPS-16`). The host keeps stdout for a short time and a user reports a bug days later. Store, in a table of their own: every 5xx (`error`); the 4xx worth a look (`warn`), but not a 401 (the client signs in again) and not a 404 that matched no route (a scanner); and successes slower than a threshold (`slow`, 3 s by default). Never a health probe, never an aborted request. A row holds the request id, the **route pattern** (never the URL or the query string), method, status, duration, the user or admin id (no foreign key), the error's machine code and a scrubbed message: no body, header, cookie, address or e-mail, never the database's `detail` (it contains the rejected value) and never the JSON parser's message (it quotes the body). Add a **trace-lite**: per request, the number and total time of database statements (including the wait for a connection) and the count and time of outbound calls by kind (an upstream HTTP call, a headless browser page), never SQL, parameters or URLs. The counter lives in the request's async context and is written only for kept rows (measured: about 5 µs for a request that is not kept, 16 µs for one that is).
- **The writer must not become the incident.** It never blocks a request; a per-minute budget per level (the proving project: 30 errors, 20 warnings, 10 slow; the rest only counted, so a storm of 4xx cannot crowd out the 5xx); a bounded queue that drops the oldest row and counts it; one multi-row insert a couple of seconds after the first queued row; back-off while the pool has waiters; a batch the database refuses as data is dropped, not retried for ever; a last flush on shutdown; **no timer while the queue is empty**. Retention by age (14 days) and by a row ceiling (20,000 rows, about 12 MB at the measured 650 bytes a row). Show the writer's counters (kept, dropped over budget, queue full, failing) on the page, quietly unless it is failing.
- **One id from the phone to the row.** The client sends its own `X-Request-Id` on every call (a retry of the same call adds `.1`, `.2`) and writes it into the bug report's step for that call, also when no answer came (the server may still have logged it). The server keeps a well-formed caller id (a short charset and length check) or makes one, and returns it in the header, the error envelope, the log line, the audit row and the request-log row. The admin's lookup by request id returns the server's rows **and** the app bug reports whose steps name it; a bug report's step links there, and the health page's view of a route links to that route's failed requests. A server older than the contract answers 400 to the unknown key in the report: the client sends the report again without ids instead of losing it. The request log is a 14-day debugging tool, not the accountability record: give it its own page beside the health and bug pages, readable with the whole-scope audit permission, and do not audit reading it.
- **Metrics that stay small and say what they cannot see** (`OPS-17`). Count per minute and per **route pattern**: status classes, sum and maximum of the duration, and a fixed latency histogram from which p50, p95 and p99 are estimated (write "estimated" on the page). Cap the keys per minute (the rest becomes `other`; a request that matched no route is `unmatched`), never count health probes, and sample process gauges (memory, event-loop delay, pool waiters, requests in flight) every few seconds. One batched upsert a minute (a restart inside the minute adds to the same row); minute rows are rolled up into hours with their own retention and a row ceiling. A health summary turns a dozen signals into ok, warn or crit over the last 15 minutes; below a minimum sample a signal stays neutral and **says "not enough data"**; each threshold is a named constant marked as a first guess. Draw a minute with no traffic as a **gap**, not as a zero. Write on the page what it cannot see: a dead server records nothing, so only an outside probe of `/healthz` notices it. (The owner of the proving project chose colours on an admin page and no alerting; that is a recorded decision against `OPS-5`, not a pass.)

## 6. Incident kit

A short section in the runbook: severity levels (S1 users cannot use the product / data at risk, down to S4 cosmetic) with who is told and how fast; roles (who commands, who writes to users); contacts; how users are told (banner, status page, in-app message); when a **post-incident review** is mandatory (data loss or exposure, S1, a rollback of a publish) and its template (timeline, cause, what worked, what changes, owners). A personal-data incident also follows the breach checklist in `privacy-and-data-rights.md`.

## 7. Maintenance, read-only and minimum version

- **Maintenance mode** is enforced on the server: writes answer 503 with `Retry-After`, reads continue where safe, the admin shows why and until when, and a banner tells users in advance. A banner alone is not maintenance mode.
- **Read-only mode** (a bad migration, a failing dependency) is a runtime control with a reason and an audit row (`runtime-controls.md`).
- **Minimum client version** for installed apps: the API tells old clients to update (a header or a 426) and the client shows an update screen instead of failing in strange ways.
- **A tab left open across a deploy** (an admin with no service worker, where nothing tells it to update): it still runs the OLD index and asks for lazy files, named by a hash, that the new deploy no longer has. A host that rewrites every path to the HTML page answers those requests with HTML, so the user sees "MIME type text/html" and the router's default error screen, typically right after signing in again with an expired session. Exclude the asset folder from the rewrite so a missing file is a real 404; reload the page ONCE when the bundler reports a preload failure (limit it to once per 30 seconds so it can never loop); and give the router its own plain-words error screen with a button instead of the library's default. Test it on a production build by answering the lazy files with HTML.

## 8. Retention of operational data

Every event or log table has a retention rule and a purge that runs under its own role and writes one "purged N rows" audit row: scrape or API telemetry, admin sessions, login attempts, uploads, exports. Without it the database grows until it is a capacity incident. The audit table has its own policy (`audit-logging.md`).

## 9. Abuse and limits

Show limiter hits and let an operator block an IP or an account for a stated time (reason, expiry, audit). Limits are read through a function so they can change at runtime within bounds. A limiter kept in one process is wrong with several instances: use a shared store or say so. Key sign-in limits per account **and** address so one office NAT does not lock out all staff. Throttle admin writes too.

**Degrade instead of queueing** (`OPS-18`). A small host and a free database fall over long before a real crowd arrives: a runaway client, a retry loop or a bug is enough.
- **A bounded pool with timers.** A maximum per instance (the proving project: 8, plus 2 for analytics) that, doubled for the overlap of a deploy, stays under the database's connection limit; a connect timeout (5 s); a client-side statement timer (20 s: a timer in the process, not a start-up parameter, which some poolers refuse); idle connections closed after 30 s. Count the jobs that hold a connection for a whole run against the pool. Migrations and purge batches get their own, longer timers.
- **Fail fast with a machine code.** Pool exhaustion, a statement timer, a database that is starting, restarting or refusing connections answer **503 `db_busy` with `Retry-After`**, with one rate-limited log line that shows the pool's state. Classify by error class and test the table both ways: a unique violation stays 409, a bad value 400, an undefined column (a bug) 500, a pooler refusing a start-up parameter 500, an analytics statement timeout 500 with its diagnostic (`OPS-11`).
- **Limit writes per user and enforce creation quotas.** A ceiling of writes per user per minute (the proving project: 120 over the whole authenticated API, mounted once after authentication; reads not counted). Quotas on every path that creates (create, import, copy, invite, accepting a join request), counted inside the transaction under a per-owner lock on the bulk paths, answered with 409 `quota_exceeded`, the resource and the limit, so the client can write the sentence in the user's language. Existing data over a new quota is never touched.
- **The client's part.** Retry a read (GET, HEAD) after `Retry-After`, at most twice, with a neutral "busy, retrying" hint only after a second and a half; never repeat a write by itself; pace an offline replay queue under the write limit and wait out `Retry-After`; never sign the user out because of a 503 (`frontend-architecture.md`).
- **Capacity limits are deploy-time values** (`runtime-controls.md` §1): keep them in one file with the reason for each number and a test for each. A variable that only a test needs (raising the write ceiling for a suite that writes hundreds of times a minute) is named as test-only.

## 10. Jobs

When a queue or scheduler exists: a state machine (queued, running, succeeded, failed, dead), retries with backoff, a dead set with retry and delete in the UI, idempotent handlers (a job returned to the queue must be safe to run again), progress and cancel for long ones, a clean stop on SIGTERM with a forced-exit timer, and an alert on queue age. Import and export jobs follow the same rules (`import-export-and-bulk.md`). If there is none, record the exclusion with its reason.

## 11. Configuration

Validate the environment at boot and refuse to start on a missing or weak required value (fail fast). Show a read-only configuration view (names and non-secret values) and an environment badge. Compare the runbook's variable table with what the code reads (the scanner lists the names) so the two cannot drift.

## 12. Multi-instance behaviour

State what is per process (caches, limiters, pause flags) and test it on **two instances**, not by simulating the second one. If that is not done, `qa-report.md` says "not verified on two instances" and the runbook says "run one instance".

## 13. A database that sleeps when idle

A serverless Postgres on a free tier suspends its compute after a few minutes without a statement and counts the time it is awake against a monthly quota. A server that touches the database once a minute for nobody keeps it awake around the clock. In the proving project a reminder loop and a metrics writer, each every 60 s, did exactly that while an outside pinger kept the host awake: the provider's usage page grew by about 6.4 compute hours in one day, about 180 a month against a free quota of 100 (`OPS-20`).

- **Loops wake, but decide in memory.** A scheduler still ticks every minute but queries only when a user request used the database since the last tick, when something can become due (computed by the previous run from what it read: a reminder window opening, a scheduled announcement), when another job already woke the database, or after a maximum sleep (6 h). The "next due" computation and the "is it due" check must be the same function, and the query must look further ahead than the longest sleep.
- **Background work never counts as activity.** Tag the jobs' queries (a flag in the async context) so that only user requests decide that "the database is awake"; otherwise a job keeps it awake by itself.
- **Write only what happened.** Metrics: only minutes with requests. The request log: a timer armed by the first queued row, gone when the queue is empty. A credential rotated every few minutes: kept in memory, written when the database is awake anyway, at once on a status change, at most once an hour otherwise, and on graceful shutdown. Purge jobs: piggy-back on an awake database, at most every 6 h.
- **Probes stay off the database.** Liveness, the public diagnostic and the root route never query it; readiness queries at boot, after a "not ready", or when a request used the database in the last minute, and otherwise answers its last result. The admin's System page still checks the database when someone opens it.
- **Prove it from outside the process.** Run the real server against a scratch database and poll, from a **separate connection**, `pg_stat_activity` for the server's connections and `pg_stat_user_tables` for any table activity every half second while health probes run: two idle windows of about two minutes show no connection and no table activity, and a reminder and a scheduled announcement still go out on time.
- **Write the trade-offs down.** A database outage during a quiet period shows on readiness only after the next real request; the first request after a quiet period pays the wake-up (a few hundred ms); after an abrupt kill, state kept in memory (the rotated credential) can be about 70 minutes older in the database. The savings are an **estimate** until someone reads the provider's usage page after a full day (the proving project estimated about 13 compute hours a month with nobody using it and 35 to 40 in typical use).

## 14. Build and release

The build that ships must be the build that was tested (`ENG-14`).
- Commit the lockfile and install with a clean install (`npm ci`), so every build gets the same versions.
- Ship compiled output, not a runtime transpiler: in the proving project the transpiler cost 215 MB at boot against 122 MB compiled (Windows working set, a comparison and not an absolute figure) on a 512 MB host. Set the heap limit explicitly, so a leak ends in a logged "heap out of memory" and a restart instead of a silent kill.
- Load every compiled module once at build time, and again with production dependencies only: a module that needs a development dependency then fails the build, not the boot.
- Run the **host's exact build command** before pushing. A project-wide type check (`tsc -b`, as the host ran it) was stricter than the one run by hand (`tsc --noEmit` on the root configuration), and the host refused a release that had passed every local check.
- CI runs the type check, the build and the smoke suites against the **built** server on a throwaway database. Each suite declares its own environment and port, the developer's own variables are removed first, a missing suite file is an error, and a suite that reported failures is retried once **with the retry printed** (a crash or a hang is never retried). A secret scan that prints only the file, line and kind runs first; a deliberate fake credential in a test carries an explicit allow marker (the first run of a new suite was red because of one). A dependency audit is reported; whether it blocks is a written decision.
- Open dependent pull requests one at a time: a branch built on an unmerged branch is rebased and opened after the first one merges, because strict CI fails on the suite files the other branch adds and nobody can tell which change broke what.
