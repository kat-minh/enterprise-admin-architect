# Changelog

## 1.10.0 - 2026-11-26

Lessons from the two days after 1.9.0, when the proving project made its backend fit to run on a small free host with a serverless Postgres on a free tier (eight merged backend pull requests about operating it) and gave its admin a health page, an integrity check of the audit, a security switch and a server log. **Guidance and gates only: no script or template changed**, so the shipped templates check none of the new views; the proving project checks them in its own suites.

- **A user's failed request can be found** (`operations-readiness.md` §5, `OPS-16`): the host keeps its log for a short time and users report bugs days later. The server keeps every 5xx, the 4xx worth a look and slow successes for 14 days, with the route pattern, a scrubbed message and a trace-lite (database statements and outbound calls by kind, never SQL or URLs), under per-level budgets and with no timer while idle. The app sends its own `X-Request-Id` per call (`.1`, `.2` on a retry) and puts it in the bug report's steps, so one lookup returns the server's rows and the reports that name the call; an older server refuses the new key with 400 and the app resends without it. A shell that probed this whole-log page for a role that reads only its own rows produced a 403 and a stored warning on every page load (`frontend-architecture.md`).
- **Metrics that stay small and say what they cannot see** (§5, `OPS-17`): per route pattern with a key cap, histogram percentiles labelled as estimates, rollups with row ceilings, signals that stay neutral below a minimum sample, idle minutes drawn as gaps, and a page that says it cannot see a dead server. The owner chose colours and no alerting; that is recorded against `OPS-5`, not passed.
- **Degrade instead of queueing** (§9, `OPS-18`; `backend-contract.md`, `frontend-architecture.md`): a bounded pool with timers that answers 503 `db_busy` with `Retry-After` (the error classes tested both ways), a write ceiling per user, creation quotas on every creating path with a machine code and the limit; the client retries only reads and never signs the user out on a 503. **Stopping cleanly** (§4, `OPS-19`): readiness 503 at once, a grace period, writers flushed before the pools close, a hard exit before the host's kill. Also a public diagnostic route with no outbound call and a system event trail (boot, shutdown, version change, migrations, retention runs).
- **Let a sleeping database sleep** (§13, `OPS-20`): a reminder loop and a metrics writer, each once a minute, kept the database awake around the clock (its usage page grew by about 6.4 compute hours in one day, against a free quota of 100 a month). Loops now decide in memory, jobs never count as activity, only minutes with requests are written, a rotated credential is written at most hourly, readiness answers from its last result while idle, and a test watches from a separate connection. The suite's own advice to point the platform probe at `/readyz` would keep such a database awake: §4 now says so.
- **A verified audit hash chain** (`audit-logging.md`, `SEC-24`): the recipe (a transaction-level lock in a trigger that fires last, a versioned canonical text, no backfill), a verify check that names the broken row and never returns content, seven tamper cases in its tests, and the limits written down (an owner who rewrites every later row passes, a cut tail is not seen; keep the last verified head outside the database). Also a streamed audit export with a hard cap refused before the first byte, and "record a change, not a call" for the end-user trail (an unchanged push subscription re-sent on every visit filled it with "enabled notifications").
- **Security switches fail closed** (`runtime-controls.md` §2-§3, `SEC-25`): a legacy sign-in path moved behind a database switch, off by default, off when it cannot be read, answering like a wrong password, with the affected accounts shown and a deploy-time variable shown as a lock; the runbook says what a code rollback does to it. Also a password change that keeps the current device signed in (`identity-and-sessions.md` §1), bootstrap password hashes out of git and a secret scan in CI (`security-baseline.md`), and a new kind of private content added to the existing audited inspect instead of a new read path.
- **Build and release** (§14, `ENG-14`) and **migrations** (§3): a lockfile, compiled output, every module loaded at build time, the host's own build command run before pushing, CI on the built server with printed retries, no stacked pull requests; a session advisory lock taken through a transaction-mode pooler can leak (found by reading the code, **not observed**); a revert keeps its migration files.
- **Light load test** (`e2e-test-playbook.md`, `PERF-9`) and **playbook**: localhost only (a hard cap otherwise), 429 counted apart from errors, the saturating resource named; the host's build command, `instanceof` across two copies of a module, deliberate fakes in a secret scan, a port left in use, one scratch database per worktree, trail tests on a production build, heavy stacks one after another, idle measured from outside the process, a real 500 by renaming a table under the running server.
- **Evidence and limits.** Measured on the proving project's own local stacks: backend `smoke:hardening-security` 46 (1 skipped), `smoke:hardening-resilience` 38, `test-db-resilience` 34, `test-shutdown` 10, `smoke:audit-chain` 60 and its unit test 24 (verify walked 50,000 rows in 5.7 s; a 50,000-row CSV streamed in about 4 s), `smoke:metrics` 35 and unit 45, `smoke:request-logs` 29 on the compiled server and unit 72 (about 650 bytes a row), the idle suite 11 (two idle windows of 98 s and 115 s with no connection and no table activity) and unit 20, `smoke:admin3` 165 and the checklist suite 54; the build pull request ran 12 suites against the compiled server, 741 passed and 0 failed; the compiled server used 122 MB at boot against 215 MB with the transpiler (Windows working set). Load test on the developer's machine: 5 users 437 requests/s at p95 26 ms, 20 users 564 requests/s at p95 103 ms, 0 errors (1,089 answers 429, counted apart, at 5 users). Admin: the health page 147, the audit system view 172 and the security switch 80 checks against a mocked API, the server log 57 checks against the real backend on a local stack, the trip checklist inspect 63; app: busy states 67, request-id unit 13. Before the idle fix the provider's usage page grew by about 6.4 compute hours in one day (read by the owner). **Not verified:** the load test ran on a local stack (compiled server and database on one 16-thread machine), not on the host, so its figures are a shape and not a capacity; on production only status codes and the deployed commit were checked (the new admin routes answered 401, the diagnostic reported the merged commit, readiness answered 200), the admin pages were not exercised on production data, and the request-log release was merged but not checked on the host; the idle savings (about 13 compute hours a month with nobody using it, 35 to 40 in typical use) are an estimate until the owner reads the usage page after a full day; a real SIGTERM from the host, the pool behind the host's pooler under load, two instances; the verify time on the hosted database; the health thresholds (first guesses); the session advisory locks behind a pooler (found by reading, not observed, not fixed); the cause of the `instanceof` failure (inferred, not reproduced). ## 1.9.0 - 2026-11-24

Lessons from the day after 1.8.0, when the owner of the proving project used its admin and said, in turn: a slow-request warning does not say where it comes from, the monitoring is thin, "I want to see which user did what, when, on which device", and "a bug must show what the user did to get it"; and, a few hours later, that signing in again after an expired session ended on an error screen. **Guidance and gates only: no script or template changed**, so the audit template does not check the new views; the proving project checks them in its own suites.

- **Telemetry must explain, not only measure** (`operations-readiness.md` §5, `OPS-13`): a page that said "p95 is 38 s" sent the operator to read code. Every job with a cheap path and an expensive fallback records the path taken and a fixed reason code; the stats show each kind split by path (count, failures, p50, p95), the reasons, a latency distribution and the slowest events; a warning names where the figure comes from. Also a rule to **list the inputs that skip the cheap path** and test them: the cause here was a request without an optional field (a new trip with no place yet) that skipped a 0.5 s request and opened a headless browser for about 40 s. The fix was checked against the live upstream first (7 queries, 0.3 to 1.3 s) and the monitoring that proves it was shipped with it. A client timeout shorter than the server's worst case, with retries, is flagged as a hazard; it was found by reading the code and **not measured**.
- **Comparable versions** (`operations-readiness.md` §4, `OPS-14`): the System panel shows the admin's version, the public app's version and the API build side by side, so the operator can compare with what a user reads on their account screen. The public app publishes a CORS-readable, uncached version file; an unreadable file is reported as unreadable.
- **End-user activity, a second trail** (`audit-logging.md`, `FN-18`): a separate table, not a widened `audit_logs`. Successful mutations and authentication events of signed-in users, the device parsed from the User-Agent by a small table-driven function (no dependency), an optional per-install id because a User-Agent cannot tell two phones of one model apart, **no IP, no content, no typed login identifier**, one middleware mapping route patterns to action keys, fire and forget, finite retention, the audit read permission reused, an `own`-scoped role refused (these are other people's records).
- **App bugs with the steps before them** (`audit-logging.md`, `FN-19`): the app keeps the last 40 steps in memory as patterns (no ids, query strings, text or tokens) and sends one report on an uncaught error; failed requests are in the activity trail with status, error code and request id; the admin merges both into one timeline. Noise rules (API errors, aborted requests, a bare "Script error.", duplicates) and a server that sanitises again, rate-limits per install, user and address, and still answers 202 when its own insert fails.
- **A stale tab after a deploy** (`operations-readiness.md` §7, `OPS-15`): an admin tab left open across a deploy asked for lazy files the new deploy no longer had, the host answered with its HTML page, and the user met "MIME type text/html" and the router's default error screen after signing in again. A missing asset is now a real 404, a failed preload reloads the page once (never in a loop), and the router has its own error screen. Found by the owner, not by a test: it appeared because several releases went out in one day.
- **Playbook** (`e2e-test-playbook.md`): back-to-back runs on one live server pollute each other's time window; a capped telemetry write must not be fed faster than its cap in a test; probe the live dependency before designing the fix; run a new test against the OLD code first (it found that the first fix was incomplete); errors thrown through the debugging protocol are muted to "Script error."; a CORS wildcard does not cover `Authorization`; a page reload empties in-memory state; parallel delegates need the shared test hook agreed in the brief.
- **Evidence and limits.** Measured on the proving project's own stack: backend `smoke:admin3` 163, `smoke:accounts` 19, `smoke:sharing` 103, `smoke:review` 80, `smoke:share` 61, the new `smoke:user-activity` 84 and `smoke:client-errors` 36, device parser 59 and report-sanitiser 46 unit checks, every list query on 50,000 rows using an index; app: the map test 5 (78 pins redrawn before the fix, 0 after), the trace test 16, travel 58, home 51; admin UIs against a mocked API: 272, 104 and 149 checks, the mocked UI audit with 0 `must`; the stale-tab test 6 (on a production build, the lazy files answered by HTML). **Not verified:** anything on the production host (including the host's own rewrite rule for the asset folder), the admin views against a real backend with real data, real User-Agent strings from phones (some in-app browser strings were written from their documented markers), a real phone or Safari. The items are rated **Guidance** and **Gate** in `docs/coverage-map.md`, not Proven.

## 1.8.0 - 2026-11-23

Lessons from finishing and operating the proving project (a consumer web app, its API and its separate admin) after 1.7.0: what the owner found by using it, and what the first production run broke. **Guidance and gates only: no script or template changed**, so the audit template still does not measure the UI items below; the proving project checks them with assertions in its own suites.

- **Stored XSS through admin-editable strings** (`security-baseline.md`, `SEC-21`): a string saved by an editor reached an attribute built by concatenation, and the old gate only tried `<` and `>`. The rule is to escape at the sink (five characters), to accept link schemes from an allow-list, and to test a payload set in every editable field on the rendered public page. Also a review item: a backslash in a JavaScript string is consumed before the SQL sees it (`'\s+'` became `'s+'`).
- **Sign-in limiter details** (`identity-and-sessions.md` §4, `SEC-22`): key IPv6 by `/64`, a per-account ceiling, an in-flight reservation before the password check, limits on reveal, inspect, reset and invitation lookup, a bounded limiter, aggregated denied-audit rows.
- **Masking is defeated by credentials and by search** (`privacy-and-data-rights.md`, `SEC-23`): credential-like fields are masked for every role; masked fields are not searchable without the reveal permission.
- **Analytics behind a connection pooler** (`analytics-endpoints.md`, `ENG-13`): a separate small pool, and the statement timeout set per transaction with `SET LOCAL`, because a start-up parameter is refused by some poolers and every analytics call then answers 500. The production fix was verified (the errors stopped); the cause was inferred, not read from the production error, and the text says so.
- **A 5xx an operator can act on** (`backend-contract.md`, `OPS-11`): request id in the UI, a safe copyable "Technical details" block for admins, and a System diagnostic that re-runs the failing path.
- **Migrations on an existing database** (`operations-readiness.md` §3, `OPS-12`): baseline instead of re-running, `lock_timeout` for DDL, a retrying database connection at boot.
- **Content versions** (`site-content-cms.md` §3, `CMS-8`): a rollback resets the draft; a draft write without a revision is refused. **Announcements** (§6): all languages in one record, scheduled sends with the tolerance stated, a lock against double sends.
- **Admin UI** (`frontend-architecture.md`, `data-table-spec.md`, `navigation-patterns.md`, `accessibility-responsive.md`, `form-spec.md`, `UX-21…24`): import the host's tokens, a written layer contract; density that moves the row (a `min-height` token alone changed nothing in lists with two-line cells) and a toolbar whose row count does not depend on its content; a centred collapsed rail; no clipped line height (≥ 1.3); setting rows in narrow containers; the product's own date-time picker for scheduled times.
- **Playbook** (`e2e-test-playbook.md`): test that a setting has a measured effect, rebuild before testing a preview build, give delegates their own ports and stop only their own processes, scope the click that answers a confirmation, and look at screenshots at five widths before writing the assertion.
- **Evidence and limits:** each item above was met and fixed in the proving project (for example its layout suite of 22 checks, its date-time picker suite of 28 checks and a push suite of 323 checks passed on its stack). Nothing was re-measured on a second stack, and the items are rated **Guidance** and **Gate** in `docs/coverage-map.md`, not Proven.

## 1.5.0 - 2026-11-21

Lessons from the fourth build session of the same project (editable roles, a CMS for the public app, an enterprise dashboard with real statistics) and from an external "admin dashboard toolkit" wish-list that was compared with the suite. The owner's feedback in that session was the test: "the dashboard is poor", "why can't the admin edit permissions", "I keep having to point out UI problems".

## 1.4.0 - 2026-11-21

A product owner noticed after delivery that the suite had no CMS-style content control, although the scan had listed the content files. An independent review of the whole suite (read-only, not anchored on that complaint) then found the same kind of blind spot in several places. This release fixes them.

**Why it was missed:** discovery never asked the owner what they change by hand today (and the gate rule discouraged asking), the `site-content` applicability test was written for brochure websites ("is this a content website?"), the scanner could not see UI strings, theme tokens, brand metadata or operations, and foundation modules could be excluded silently.

- **Discovery:** an **owner intake** (five closed questions, outside the 7-question gate cap), a **content & configuration inventory** with mandatory rows (UI strings, branding, legal pages, SEO, e-mail/SMS/push copy, pricing constants, banners, switches, sample content, metric sources), mining of manual operations (scripts, runbooks, data-fixing migrations), walking the authenticated journeys, and the rule that "settings" or "CMS" is disambiguated before analysis. Every excluded foundation module becomes a yes/no question at Gate 1. New `admin-discovery/references/site-content-and-config.md` (three tiers, applicability test for apps and websites, keep-in-code / override-layer / external-CMS, one owner per entity, permission split by risk).

- **Validator:** warns when `product-discovery.md` has no Owner intake or Content & configuration inventory, when the Feature Ledger has no `Owner module` column, a blank or unknown owner; lists foundation modules that are neither included nor excluded with a reason (a template placeholder row decides nothing); warns when a module spec lacks "Public-site integration". ## 1.3.0 - 2026-11-21

- Dashboard design: state the window ("24 hours" as 24 buckets vs rolling), round axis labels (maximum must be even when the axis shows 0 / half / max), work-queue card layout.
